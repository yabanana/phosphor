## 1. Layering models

### 1.0 Vocabulary from the two standards that matter

* **MaterialX PBR spec** distinguishes **horizontal layering** (`<mix>`: "per-shading-point linear mixing of different BSDFs where a mix factor is given per BSDF"; the weight "can be used as a mask") and **vertical layering** (`<layer>`: a top BSDF over a base BSDF; "the light not reflected by the top layer is assumed to be transmitted to the base layer"). [V] https://github.com/AcademySoftwareFoundation/MaterialX/blob/main/documents/Specification/MaterialX.PBRSpec.md (section "Layering"; raw: https://raw.githubusercontent.com/AcademySoftwareFoundation/MaterialX/main/documents/Specification/MaterialX.PBRSpec.md)
  * `mix`: `f = (1-w) f_bg + w f_fg`; vertical-layering transmittance mixes the same way `T = (1-w)T_bg + wT_fg`; "Because w in [0,1], the mix of two individually energy-conserving distribution functions is also energy conserving." [V] same file, `### mix`.
  * `layer`: `f = f_top + T_top f_base`, `T = T_top T_base`; associative; "if f_top and f_base are individually energy conserving, the layered result is also energy conserving"; for an interface BSDF `T_o = 1 - E_o` (directional albedo of reflection lobes); an opaque BSDF with weight 0 is transparent to layering, weight 1 occludes the base, and "layering an opaque BSDF over a base is equivalent to a mix of the two BSDFs with the coverage as the mixing weight". Invariant `E_o <= 1 - T_o`. The spec says `T_o` is a fixed-exitant-direction approximation of the pass-through factor of Weidlich and Wilkie's layered microfacet model. [V] same file, "Vertical-Layering Transmittance" and `### layer`.
* **OpenPBR** (Academy Software Foundation): slab formalism; `layer(S_sub, S_coat)` uses the albedo-scaling approximation `f_layer = f_coat + (1 - E_coat) f_sub`, with `E_layer = E_coat + (1-E_coat)E_sub <= 1` and a white-furnace pass if `E_sub = 1`; coat darkening `f = f_coat + T^2_coat (1-E_coat) f_sub`; `mix(S0,S1,w1)` with `M -> S0` as `w1 -> 0` and `M -> S1` as `w1 -> 1`, reduced BSDF `lerp(f0,f1,w1)`; "layer presence" weight: `layer(S_sub,S_coat,w) = mix(S_sub, layer(S_sub,S_coat), w)`. Documented limits: albedo scaling ignores inter-layer multiple bounces and coat absorption/scattering. Mixing physically inconsistent bulks (dielectric vs metal) is ambiguous. [V] https://academysoftwarefoundation.github.io/OpenPBR/ (Formalism: Slabs / Layering / Mixing; first 100k of 177k chars read; Model section gives the stack `surface = layer(coated_base, fuzz, F)`, `coated_base = layer(base_substrate, coat, C)`, `base_substrate = mix(dielectric_base, metal, base_metalness)`).
* **Weidlich & Wilkie, "Arbitrarily Layered Micro-Facet Surfaces" (GRAPHITE 2007)**: the academic basis for the vertical model; I did not open the paper. [U] (DOI not verified in this session; the MaterialX spec cites it as `[^Weidlich2007]`, so the reference list in https://github.com/AcademySoftwareFoundation/MaterialX/blob/main/documents/Specification/MaterialX.PBRSpec.md has the exact citation.) Its relevance for F15 is limited: vertical coat of a terrain "finish" is a thin-coat case where albedo scaling is the accepted cheap form (see OpenPBR above).

### 1.a Parameter-space blending (lerp parameters, evaluate one BSDF)

* **What it is**: `p = sum_i w_i p_i` for albedo, roughness, metallic, occlusion, normal etc., then one GGX+Lambert evaluation.
* **Validity**: Epic describes exactly this as an *approximation* used for simplification: Substrate "progressive tree simplification using parameter blend of slabs descriptions based on some empirical rules" and "a way to parameter blend horizontal mixing is a simple lerp of the parameters". [V] https://advances.realtimerendering.com/s2023/2023%20Siggraph%20-%20Substrate.pdf (slides text, notes on the "simplification" slides). Epic's docs also list a "parameter blending" option that "reduce[s] memory use substantially" (four-slab material 108 to 28 bytes per pixel) and make lighting cheaper. [V] https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-substrate-materials-in-unreal-engine
* **Energy (my analysis [D])**:
  * Albedo, F0, AO, metallic, roughness each stay in [0,1] under a convex combination, so every *bounded* input stays in its valid range. That is a necessary condition, and it is the whole of what the MaterialX proof gives for BSDF mixing; it is not a proof for parameter blending.
  * The glTF base model is not linear in its parameters. Diffuse term is `c (1-F0_eff-ish Fresnel)(1-metallic)`: a product of two lerped quantities (`lerp(c)·(1-lerp(F))`) differs from `lerp(c·(1-F))`; both factors are <= 1 so the product stays <= 1 (bound preserved), but the *value* differs from BSDF mixing by a cross term. GGX `D(alpha)` is strongly nonlinear in roughness: the average of two lobes (BSDF mix) is bimodal, a lobe at the averaged roughness is unimodal. Both integrate to at most 1 for a single-scatter GGX (single-scatter GGX loses energy at high roughness, which is why MaterialX/Substrate add Turquin multi-scatter compensation: [V] MaterialX spec "Energy Compensation"; Substrate slides "rely on Turquin's approach"). Blend roughness in the same variable the BRDF uses (alpha = r^2 or perceptual roughness) and accept the difference; it is a look decision, not an energy decision.
  * Metallic: glTF defines the base as `mix(dielectric_brdf, metal_brdf, metallic)` (see clearcoat README below), so lerping `metallic` between a metal layer (1) and a dielectric (0) *is* exactly the BSDF mix at the layer level, provided baseColor is the shared input as the glTF model defines. A lerped metallic in (0,1) between two layers still represents a physical "partially metallic" mix (patches), as glTF already allows.
  * Normals: a lerped normal is a shorter vector; it must be renormalised and it flattens detail at mid weights (see section 2). Its shading energy is bounded (it is still a unit normal), but contrast is lost.
  * Aggregates: occlusion/AO and any scalar "strength" are linear and safe.
* **Cost**: N layers sampled per pixel (each layer = albedo + normal + ORM = 3 fetches, or 2 with packing as in section 5), **one** BSDF evaluation. Lighting cost independent of N; storage in the G-buffer or visibility-buffer resolve is independent of N. Epic: "each additional BSDF per pixel slows lighting proportionally" (hence parameter blending to cap it). [V] Epic overview URL above.
* **Default in**: glTF's own `mix(dielectric, metal, metallic)` structure; Unreal landscape layer blending (LB Weight/Alpha/Height Blend produce one set of material attributes per pixel) [V] https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-materials-in-unreal-engine; Unity HDRP LayeredLit/Terrain Lit (layers are HDRP Lit materials combined into one surface; up to four layers) [V] https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@17.0/manual/layered-lit-material.html. Activision's terrain composites layers into virtual-texture pages holding albedo/normal/occlusion/gloss/metalness, i.e. one resolved parameter set per texel [V] https://advances.realtimerendering.com/s2023/Etienne%28ATVI%29-Large%20Scale%20Terrain%20Rendering%20with%20notes%20%28Advances%202023%29.pdf .

### 1.b Shaded / BSDF-space mixing (weighted sum of BSDFs)

* **What it is**: `f = sum w_i f_i`, each with its own normal, roughness, F0. Needs N BSDF evaluations (or N lobes in the G-buffer).
* **Validity/energy**: physically "patches of different materials" (OpenPBR: "randomly distributed mesoscopic patches of each material, in proportion to the weight") [V] OpenPBR URL above; energy-conserving by construction for weights summing to <= 1 (MaterialX proof above, extends to N by induction [D]). Each layer can keep its own normal; correct for mixed dielectric/metal.
* **Cost**: N lighting evaluations; Epic: two BSDFs "about twice as long as for one" [V] Epic overview URL. Epic therefore bounds closures per pixel (project setting `Substrate Closure Per Pixel`; over-limit materials "are iteratively simplified") [V] same URL, and Substrate falls back to parameter blending when the closure count exceeds the budget [V] Substrate slides.
* **Used by**: Substrate Horizontal Mix (when budget allows), Blender/MaterialX/OpenPBR as reference semantics, offline renderers.

### 1.c Vertical layering (coat over substrate)

* **Models**:
  * glTF `KHR_materials_clearcoat`: `mix(base, coat_brdf, weight * fresnel)` with `fresnel` computed from `N.V` of the coat normal ("to be energy conserving with a simple layering function, we compute the microfacet Fresnel term with NdotV"). Limits stated by the spec: coat infinitely thin, no refraction, IORs independent, no scattering between layers; emission is under the coat and darkened. [V] https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_materials_clearcoat (README read through `gh api`; lines on "fresnel_coat", "Layering", "Energy conservation").
  * MaterialX `layer` and OpenPBR coat: albedo scaling (above).
  * Substrate Vertical Layer: top slab with thickness, absorbing medium; Epic notes the bottom's appearance depends on the top. [V] Epic overview URL.
* **Validity**: valid for a thin dielectric top (coat, wet film, varnish); not for opaque top layers (an opaque top with coverage is just a horizontal mix per MaterialX [V]). Albedo scaling is accurate to first order only (OpenPBR states no inter-layer bounces).
* **Energy**: `E = E_top + (1-E_top)E_base <= 1` [V]. Cost: top BSDF + base BSDF evaluations (2 lobes) plus a directional-albedo lookup for the top (precomputed table in Substrate/MaterialX; a Schlick/analytic approximation is permitted: glTF says implementations "can vary based on device performance"). [V] clearcoat README and Substrate slides ("precomputed table of directional albedo").
* **Used by**: every PBR engine for clear coat; Unreal/Substrate as the default for coat-type materials; glTF via KHR_materials_clearcoat.

### 1.d Height-based blending with contrast

* **Mishkinis (Gamasutra 2013)**: each layer has a height `h_i` summed with its opacity `a_i`; `ma = max(h_i + a_i) - depth` (depth = 0.2 in the example); weight `b_i = max(h_i + a_i - ma, 0)`; result = sum(b_i c_i)/sum(b_i). [V, structure from the fetched summary of the original article; code not reproduced verbatim] https://gamedeveloper.com/programming/advanced-terrain-texture-splatting . Behaviour at the endpoints: *not exact* (the article does not state it; a layer at opacity 0 can still win if its height exceeds the other layer's height+opacity by more than `depth`) [D]. Therefore the published formula alone does not give "layers equal the single material at weights 0/1"; an endpoint-exact variant is needed (section 6).
* **Engines**: Unreal `LB Height Blend` ("same as weight blend but adds detail to the transition via a height map"; known artefacts: black spots where several height-blended layers meet, invalid (0,0,0) normals) [V] https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-materials-in-unreal-engine ; Unity HDRP LayeredLit `Use Height Based Blend` + `Height Transition` slider (blend size), plus `Layer Influence Mask` for main-layer influence on albedo/normal/height of upper layers; Terrain Lit renders (approximately) the layer with the greatest height. [V] snippets from https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@15.0/manual/Layered-Lit-Shader.html and the Layered Lit inspector reference (full property list not read, [U] for exact property semantics).
* **Energy**: a normalised weight vector `b_i/sum b` is convex, so it inherits the parameter-blend (or BSDF-mix) properties above; it does not itself create or destroy energy. Its failure mode is the divide-by-zero when all `b_i = 0` (Epic's black spots/(0,0,0) normals; Mishkinis avoids it because the top layer's weight is always equal to `depth`) [V for Epic; derived for Mishkinis from the fetched structure].
* **Contrast loss**: linear texture blending reduces variance (about half at the midpoint for uncorrelated textures); Laplacian blending is a published remedy at n+1 samples per texture. [V] Wronski, "GPU-Friendly Laplacian Texture Blending", https://arxiv.org/html/2502.13945v1 (author per https://arxiv.org/abs/2502.13945).

## 2. Normal blending

Notation: `b` base, `d` detail, both unpacked to [-1,1]. All from Barré-Brisebois & Hill, "Blending in Detail" (2012) [V]: https://blog.selfshadow.com/publications/blending-in-detail/ .

| Method | Formula | flat detail (0,0,1) returns base | flat base returns detail |
|---|---|---|---|
| Linear | `normalize(b + d)` | no | no |
| Partial derivative | `normalize(b.xy d.z + d.xy b.z, b.z d.z)` | yes | yes |
| Whiteout | `normalize(b.xy + d.xy, b.z d.z)` | yes | yes |
| UDN | `normalize(b.xy + d.xy, b.z)` | yes | **no** (detail z lost) |
| RNM | `t=(b.x,b.y,b.z+1)`, `u=(-d.x,-d.y,d.z)`, `normalize(t (t.u)/t.z - u)` | yes | yes |

Notes:
* "Weights 0 and 1" for a *layer stack* are not the same as "flat detail": the question is what a weighted combination of N normals returns when one weight is 1. Methods above combine two maps (base+detail), they are **overlay** operators, not **weighted mix** operators. For a stack with masks you need a weighted form. **Reorienting** (RNM/whiteout) each layer's tangent normal onto a shared base frame is orthogonal to weighting.
* **Surface gradient framework** (Mikkelsen, JCGT 9(3), 2020) [V]: https://jcgt.org/published/0009/03/04/paper.pdf . Properties used: the surface gradient is a linear operator, independent of the parameterisation (eq. 13-14); the framework: scale each gradient, **add** gradients, resolve with `normalize(n - sum_i s_i g_i)` (Listing 1: `ResolveNormalFromSurfaceGradient(g) = normalize(nrmBaseNormal - g)`). A tangent-space normal `m` converts to a derivative `d = (-m.x/m.z, -m.y/m.z)` and `n' = n - (t d.x + b d.y)` (eq. 17), then `g = t d.x + b d.y` (TBN-style, Listing 3). The paper shows this is "order-independent blending" and explicitly motivates it by material layering and multiple UV sets with only one stored tangent space. Triplanar weights: the paper accumulates gradients with weights `w` (Listing 13/14).
  * Weighted layer blend: `g = sum_i w_i g_i`, `n = normalize(n_geo - g)`. **With weights `w_j=1`, others 0: `n = normalize(n_geo - g_j)` = exactly that layer's own perturbed normal** (by eq. 17 identity; exact up to normalisation). With all `w=0` the result is the geometric normal (flat), which fixes Epic's invalid (0,0,0) normal problem [D, follows from Listing 1]. A flat layer (m=(0,0,1)) has `g=0`, so blending with a flat layer attenuates the other's bump linearly (a desired "reduce bump strength" semantic).
  * For `sum w_i = 1`, this equals partial-derivative blending in the special case of two maps sharing one frame and weights as scale factors [D; the paper cites Blending in Detail, ref [Barré-Brisebois & Hill 2012] in its bibliography].
* **Tangent frames**: gradients are only comparable if they are expressed in the same surface frame. Per layer the tangent-space normal must be converted with *that layer's* UV frame (tiling, rotation, triplanar axis, hex-tiling rotation) to a gradient in the geometry frame, then summed. mikkTSpace requires the interpolated *unnormalised* vertex frame; the paper's trick is to scale `t,b,n` by `1/|n|` so that the normalised-normal formulation stays mikkTSpace-compliant. [V] JCGT paper, section 3.2. If layers have different UV scales, scale-dependent bump conversion applies (the paper's `SurfgradScaleDependent`, section "scale dependent", [V] listing exists at JCGT line "float3 SurfgradScaleDependent"; details not read). A **per-pixel derivative frame** (no stored tangents) is also provided by the paper (Listing 4). [V]
* **Correct at weight 0/1** (exact equality to the single layer's normal): surface-gradient weighted sum **yes** [D from eqs. above]; RNM/whiteout **yes** only as an overlay with flat second operand; linear **no**; UDN **no** when base is flat; renormalised linear lerp of normals `normalize(sum w_i n_i)` **yes at exact weights 0/1** (it returns `n_j`) but fails the flat-neighbour/frame mismatch property and is only valid when all `n_i` are in the *same* frame (otherwise not meaningful). So the cheap valid baseline is: convert every layer's normal to the common frame (tangent-space → world with the layer's frame) then either (A) gradient sum, or (B) renormalised lerp in world space.

## 3. Masks, stack bounds and cost bounding

* **Mask sources**:
  * painted weight maps: Unreal packs four layers per weightmap texture ("a new weightmap texture is added for every 4 target layers, since each RGB8 channel holds one layer") and caps painted weights at 1.0 (paint tools scale others down). [V] https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-materials-in-unreal-engine
  * vertex colour: Unity HDRP LayeredLit `Vertex Color Mode` modes combine layer mask with vertex colour (None = mask only). [V] snippets via search; full list [U].
  * height: sections 1.d.
  * procedural slope / curvature / cavity: Frostbite 1 "procedural shader splatting" chose materials from height and slope instead of stored masks to avoid mask textures. [V as described in the DICE notes via search snippet] https://frostbite.com/frostbite/news/terrain-rendering-in-frostbite-using-procedural-shader-splatting ; course notes https://advances.realtimerendering.com/s2007/Andersson-TerrainRendering(Siggraph07)-CourseNotes.pdf (full text not read; the year printed on a forum mirror differs, [U]).
* **Typical bounded stack sizes**:
  * Unity HDRP LayeredLit: **4** layers (main + 3). [V] URL above.
  * Unreal Landscape: no hard documented layer limit on desktop/console; mobile ES3.1 has a 16-sampler limit across the whole material, recommended **3** layer nodes; each component gets its own material instance and "if a component doesn't use a layer, that layer's node subtree is discarded" (per-component sparse stack). [V] Epic landscape URL.
  * Activision (BO Cold War): early system had an alpha mask per layer, "32 layers", "Expensive & unpredictable shaders" because "nothing prevent[ed] all 32 layers from being used to shade a single pixel"; replaced by **One Material Per Vertex**: a 1-byte index map (most prominent layer) + BC1 colour tint, "Bounded GPU cost", up to 256 layers; each pixel gathers the **4 surrounding vertices**, merges duplicate layer indices by summing their alphas (so typically 1 material sample, up to 4 with tile hiding), the first layer is never blended (alpha 1), others blend with artist "reveal maps". Next step: Multi-Layered Terrain Materials (2 materials + threshold + reveal map, authored transitions at run time). [V] Activision slides text: https://advances.realtimerendering.com/s2023/Etienne%28ATVI%29-Large%20Scale%20Terrain%20Rendering%20with%20notes%20%28Advances%202023%29.pdf
  * Terrain3D (open source editor): all splat maps sampled, strongest **4** of 16-32 blended per pixel. [U: search snippet only] https://terrain3d.readthedocs.io/en/latest/docs/shader_design.html
* **How cost is bounded**: (1) fixed max N per pixel, enforced by the representation (4 weights per RGBA texel, top-K per pixel); (2) sparse layer lists / per-component dead-layer elimination (Unreal) [V]; (3) merging duplicates (Activision) [V]; (4) classification of pixels into permutations by active-layer set (what Phosphor's function-constant permutations would do; Substrate has a "material classification pass" with small fixed overhead that reduces lighting cost, [V] Epic overview URL); (5) **cache the composite**: Frostbite BF3 splatted into a virtual texture because shader splatting "rendering very slowly (10-20ms)", then full-screen rendering from the texture cost 2.5-3 ms (PS3), tile compositing 0.2-0.5 ms; [V, read in PDF] https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/gdc12-terrain-in-battlefield3.pdf ; Activision also renders terrain layers with a compute shader into VT pages [V]. Wronski suggests the same for terrain: blend into a cached virtual texture instead of at run time. [V] https://arxiv.org/html/2502.13945v1

## 4. OpenPBR / MaterialX semantics, and glTF

* **MaterialX**: `mix(bg, fg, w)` = `bg(1-w) + fg w` for BSDF/EDF/VDF; `layer(top, base)` = `f_top + T_top f_base`; `add`, `multiply` have **undefined transmittance composition** in the current spec ("reserved for a future revision"). [V] MaterialX PBR spec raw URL above. Also: MaterialX `mix` on `surfaceshader` type is supported by code generators (a changelog mention; [U]).
* **OpenPBR**: see 1.0 for formulas. Key take-away for a terrain stack: *coverage* weights are a `mix` (horizontal); a coat painted in cavities is `layer(sub, coat, w_coat)` which OpenPBR defines as `mix(sub, layer(sub,coat), w_coat)`, i.e. a weighted lerp between "no coat" and "coat". [V]
* **Substrate (Unreal)**: operators = Horizontal Mix (lerp, per pixel, Mix may be texture), Vertical Layer (top thickness), Coverage Weight (alpha-like), Add (explicitly not energy-conserving: "can emit more energy than it receives" and best avoided), Select. [V] https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-substrate-materials-in-unreal-engine . Substrate states that this tree "would not be possible to do with a soup of BSDF as proposed by MDL or MaterialX" because the slab is a principled representation that can be parameter-blended (statement from the Substrate slides, [V]); it uses a statistical aggregate (transmittance, coverage, roughness, refraction lobe) assuming no correlation between slab coverages. [V] Substrate slides.
* **glTF**: there is **no ratified layering extension** [V]. The registry directory of ratified/in-progress Khronos extensions has these material extensions only: anisotropy, clearcoat, diffuse_transmission, dispersion, emissive_strength, ior, iridescence, retroreflection, sheen, specular, transmission, unlit, variants, volume (list from `gh api repos/KhronosGroup/glTF/contents/extensions/2.0/Khronos`, queried 2026-11-13) https://github.com/KhronosGroup/glTF/tree/main/extensions/2.0/Khronos . Open PRs I found (all unratified, drafts): `KHR_materials_coat - "Advanced Coat"` (PR #2534, "an attempt to bring compatibility with OpenPBR's coat layer", would replace clearcoat and its sub-extensions) https://github.com/KhronosGroup/glTF/pull/2534 ; `KHR_materials_clearcoat_ior/_color/_anisotropy` (#2530, #2520, #2528); `EXT_materials_bump` (#2339); `KHR_texture_procedurals` (#2381, a procedural-texture graph proposal, could carry masks, not read); `Proposal for vertex attribute based PBR materials` (#1235, not read). No `KHR_materials_layer*` or blend/stack proposal was found by `gh search` (title/body search "layering", "layer"; may miss untitled drafts). [V] https://github.com/KhronosGroup/glTF/pulls . The glTF base model is itself `mix(dielectric_brdf, metal_brdf, metallic)` and clearcoat is `mix(base, coat, weight*fresnel)`. [V] clearcoat README.
* **How a glTF-based engine can express a stack**: with no standard, use a private extension (e.g. `PHOSPHOR_materials_layers`/engine-side asset) listing N child material references (each a plain glTF PBR material, so each layer is losslessly "equivalent to the single material"), mask sources, blend mode (weight/height/alpha), and per-layer coat flags mapped to `KHR_materials_clearcoat` semantics. Mark any such extension vendor-prefixed (`EXT_`/private), not `KHR_`. [D]

## 6. Recommendation: bounded, testable baseline for F15.4

**Representation**
* Stack of **K = 4 layers per pixel** from one RGBA8 weight texture (one texel = 4 weights; matches Unreal's 4 layers per weightmap texture and Unity's 4-layer cap) with **top-K=4 selection** if the authored stack has more layers than 4 (renormalise after pruning, optionally per tile). Larger stacks = multiple weight textures but still K<=4 non-zero per pixel after pruning. (K=8 as an explicit opt-in only after a measured cost spike.)
* Layers are plain glTF PBR materials (same parameter set as the single-material path), so "weight 1 = single material" is testable by construction.
* One extra **coat/finish layer** (vertical) allowed on top of the blended base: weight `w_coat` (painted/cavity mask) with `fresnel_coat`-style albedo scaling as in glTF clearcoat and OpenPBR (`f = w f_coat + (1 - w F_coat-ish)...` use the OpenPBR weighted-layer form `w_coat f_coat + lerp(1, T^2(1-E_coat), w_coat) f_sub`, optionally with T^2 = 1).

**Blend space**
* **Parameter space** (1.a) after per-layer evaluation: albedo (linear space, not sRGB), roughness (in the BRDF's own variable), metallic, AO, emissive, F0/specular factors by lerp; **one BSDF evaluation per pixel** (matches the "no uber-shader, permutations by function constants" policy: permutation key = bitmask of active layers + coat on/off + height blend on/off). Horizontal BSDF mixing (1.b) is reserved for the rare case of conflicting lobes (e.g. glass vs metal) and is out of baseline scope.
* Height blending: endpoint-exact variant [D, my proposal, not a published method]: `w'_i = w_i e^{k h_i} / sum_j w_j e^{k h_j}` (k = contrast, `h_i` in [0,1] centred, e.g. `h_i - mean`). Properties: `w_i = 0` gives `w'_i = 0`; a single `w_j = 1` gives `w'_j = 1`; it reduces to plain weights at `k = 0`; denominator is non-zero whenever `sum w > 0` (no Epic-style black spots). Keep a floor for `sum w = 0` (fall back to layer 0). Compare against Mishkinis' `max(h+a)-depth` variant in the spike, but note the latter is not endpoint-exact.

**Normals**: surface-gradient accumulation (Mikkelsen): per layer convert the tangent-space normal with *that layer's frame* to a gradient `g_i = t_i d_i.x + b_i d_i.y` (`d = -m.xy/m.z`), `g = sum w'_i g_i`, `n = normalize(n_geo - g)`; coat layer normal is its own (glTF: coat normal affects the top layer only). This is exact for the single layer at weight 1, yields the geometric normal for no coverage, and handles different UV scales/rotations/triplanar. Baseline fallback if gradient frames are unavailable: world-space renormalised lerp.

**Energy rule**: weights normalised to sum to 1 for the base blend (coverage sum <= 1 and remainder assigned to layer 0 or to "base" layer); every layer input clamped to its valid range before blending; coat via albedo scaling `E_layer = E_coat + (1-E_coat)E_sub <= 1` (OpenPBR/MaterialX). Single-scatter GGX loses energy at high roughness: use whatever multi-scatter compensation the engine already applies, applied *after* blending (once), so that blending does not change the compensation behaviour. No additive operator (Substrate marks `Add` as not energy conserving). [V]

1. **Weight 0/1 equality**: for each layer `j` and for random layer parameters, weights `e_j` return, bit-for-bit within float epsilon (tolerance ~1e-6 on parameters, 1 ulp-ish on normal), the single material's parameter set; with the height blend active and with the coat weight 0 it equals the uncoated result; coat weight 1 equals the `fresnel_coat` layered reference. GPU: rendered pixel diff against the single-material pipeline = 0 pixels (use `image_diff` as already done in OPT-1 and `tools/variant_check.sh` style).
2. **Normal equality**: weights `e_j` give the layer's own normal (compare against single-layer pipeline); all-zero weights give the geometric normal; mixed layers with different UV rotation/scale give gradients that add (check linearity `g(w a + (1-w) b) = w g(a) + (1-w) g(b)`); frame check: rotating a layer's UVs by an angle rotates its normal contribution consistently (consistency with the per-vertex mikkTSpace frame).
3. **Monotonic transitions**: along a 1-D mask ramp `t in [0,1]` for two layers, each parameter `p(t)` is monotone between `p_0` and `p_1` (parameter lerp; with height blend, weights `w'_i(t)` monotone in `t` for fixed `h`, k >= 0). Property test over random parameter sets; weights always sum to 1 (+/- epsilon) and are in [0,1]; no NaN for any weight input including all zero.
4. **Energy bound in white furnace**: for random valid parameter sets and weights, directional albedo `E(v) = integral f cos` of the *blended* single BSDF (numerical integration over the hemisphere, include coat) satisfies `E <= 1 + eps` for all `v`; with white furnace at `baseColor=1`, `roughness` in [0,1], `metallic` in {0,1} the blended result is `<= 1`; compare blended `E` to the weighted sum of the layers' `E_i`: record the deviation (parameter-blend vs BSDF-mix) as a regression number with a tolerance, since parameter blend is an approximation (Epic, section 1.a). Include a negative control that must fail: an additive combination of two layers (`f_1 + f_2`) must exceed 1.
5. **Permutation consistency**: every active-layer-set permutation (function-constant variant) renders identically to the generic path (existing variant_check pattern), including layers with weight exactly 0 (the permutation that drops a layer must equal the generic path where its weight is 0).
