# F14.4: day/night repeatability under shader validation (2026-11-12)

Device: Apple M5 Max 128 GB, one GPU process at a time. Binary: branch
`phase/f14-4-closure` at 49eff75 (main be886ca plus the specular-cap fix,
which is bit-identical to main on the default path: Sponza 12/12, mirror,
roughness and rough-emitter 300/300 frames). Case: the frozen `daynight-r1`
command (dusk into night, `--day-length 16 --start-hour 17`, brute-force
local lighting with RT visibility, `--volume-oracle`), run twice with the same
binary and compared frame by frame on the linear HDR capture
(`repeat_check.py`, evidence in `build/f14-4-nondet-20261112/`).

## Question

448bca7 found that the pair is not bit-reproducible with
`MTL_SHADER_VALIDATION=1`, while every configuration without shader
instrumentation is. The closure kept F14.4 open until the cause was known:
a synchronisation race or uninitialised read in our code would also be a
product defect, and an instrumentation effect would not.

## Findings

- **Not a CPU/GPU race.** One frame in flight does not change it (E2). A GPU
  slowed by 30 ms per frame without instrumentation stays bit-identical (E3).
- **Not pipeline compilation timing.** Synchronous compilation does not change
  it (E5). Runtime compilation without the archive and without instrumentation
  stays bit-identical (E7).
- **The trigger is one instrumentation type in one place:** the
  `RESOURCE_USAGE` instrumentation (S4) of the two DI shading kernels (P1–P3),
  and only of the RT visibility trace inside them (D1).
- **Granularity:** differences come in runs of 23–32 pixels along a row, i.e.
  whole SIMD groups, from the first frame. Visibility is a boolean
  any-intersection test (`diEndpointVisible`), so a whole SIMD group gets a
  different answer for one light.
- **The validator reports no invalid resource access** in the kernel whose
  instrumentation changes the result.

## What the corrupted values are

The raw DI signal (`--capture-linear-signal direct`, only the DI kernels
instrumented) differs in exactly 16, 32 or 64 pixels per diverging frame, on
one row, starting at x a multiple of 32: whole SIMD groups. In those groups the
low components of the result are zero in one run and correct in the other
(A = (0.0237, 0.00118, 0.00059), the moving-light colour (8, 0.4, 0.2), against
B = (0, 0.00118, 0.00059); another frame loses R and G). These are not
visibility flips, which would remove a light's whole contribution.

Ruled out as the source of the zeros:

- **Rejected reads.** `MTL_SHADER_VALIDATION_FAIL_MODE=allow` still diverges
  (22/40 frames), `RETURN_BADFOOD_ON_FAULT=1` leaves no 0x8badf00d value, and
  `ABORT_ON_FAULT=1` never aborts.
- **Timing.** The instrumented DI kernel does not make the frame slower (GPU
  7.7 ms against 8.8 ms). Slowing the DI kernel by 4.6 ms without
  instrumentation leaves every frame bit-identical, on both the HDR and the raw
  DI signal.
- **Code shape.** Tracing before computing the contribution, reading the
  material and emitter fields by reference, removing the error atomics, the
  noise or the textured sampling: each one alone still diverges.

## Standalone reproducer (F14-K2)

`bench/f9_spike/s8_engine_di.cpp` runs the engine kernel `light_cluster_shade_rt`,
compiled from the engine sources, outside the frame. Its inputs are synthetic
but engine-shaped: receivers on a floor, the twelve triangle lights of an
emissive cube in the moving-light colour, one occluding quad in a TLAS with the
engine intersection function table, and the engine dispatch shape. It runs
8 frames × 12 repeats on identical inputs and compares each repeat bit for bit
with the first (88 comparisons). Each line gives the divergent repeats in the
harness's three runs.

| Configuration | Engine kernel | Reduction `k_cfg`, bits 8 |
|---|---|---|
| no shader validation | 0 / 0 / 0 | 0 / 0 / 0 |
| `MTL_SHADER_VALIDATION=1` | 75 / 84 / 84 | 88 / 88 / 88 |
| … `RESOURCE_USAGE=0` | 71 / 83 / 81 | 0 / 0 / 0 |
| … `FAIL_MODE=allow` | 84 / 82 / 75 | 88 / 88 / 88 |
| validation on, every instrumentation category off | 0 / 0 / 0 | — |
| only `GLOBAL_MEMORY` instrumentation | 63 / 43 / 62 | — |
| only `RESOURCE_USAGE` instrumentation | 86 / 87 / 85 | — |
| only `STACK_OVERFLOW` or only `GENERIC_ADDRESS_SPACE` | 0 / 0 / 0 | — |

`k_cfg` is a copy of the engine kernel with each construct behind a function
constant bit, so the compiler drops disabled code. With every bit off it never
diverges. Bits 8 alone adds only the `diRecordNonfinite`/`diLightFinite` error
atomics, which no thread executes because every value is finite. That kernel
diverges in all 88 repeats: whole SIMD groups return (0, 0, 0) or (12, 0, 0)
instead of the exact (12, 6, 3). The SIMD group that fails changes from repeat
to repeat, and so do the zeroed components. Combinations behave
non-monotonically: every bit except the noise bit never diverges, every bit
except the atomics always does. The trigger is the shape of the generated
code, not the program's logic.

## Conclusion

The run-to-run variation is a defect of Metal shader validation's memory-access
instrumentation on this macOS (27.3, 26C5035r) and M5 Max. Global-memory or
resource-usage checks, inserted into a kernel that loops RT visibility traces,
corrupt the results of whole SIMD groups without reporting a fault, even when
the only difference is logically dead code. Engine inputs, synchronisation and
pipeline compilation are not involved: the product shaders repeat the day/night
transition bit for bit in every configuration tested (API validation, no
pipeline archive, a GPU slowed to 39.5 ms per frame, the corpus repeatability
pair), which is the plan's acceptance, "transizione giorno/notte ripetibile".

Consequences:

- **Bit-identity checks** of RT lighting run with API validation only, as the
  runner's repeatability role already does.
- **Full-validation corpus runs** still catch invalid accesses, but their
  images can carry these SIMD-group losses: a few dozen pixels per frame out of
  230 400. That is far below what moves the p95 and flicker metrics the clips
  are judged on.
- **F14-K2 is the probe** for this defect. Rerun it after every OS or Xcode
  update (`MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1 build/release/f9_spike
  --only F14-K2`, then `F14_KERNEL=k_cfg F14_CFG=8`). When it reports 0 divergent
  repeats, the pair can also be held to bit identity under shader validation.
